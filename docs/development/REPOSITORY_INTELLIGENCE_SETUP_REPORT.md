# Repository Intelligence Setup Report

Branch: `feature/repository-intelligence-map`. Date: 2026-08-03. Base:
`dev/bess-calc` (`549e01c`). This is infrastructure work only — no product
code, API, database schema, or business logic was changed.

## Installed tools

- **madge** (`bess-calc/package.json` devDependency) — TypeScript-aware
  import graph extraction. Zero-config beyond `--ts-config tsconfig.json`;
  outputs JSON and can detect circular dependencies (`--circular`).
- **dependency-cruiser** (`bess-calc/package.json` devDependency) — rule-based
  dependency validation with pass/fail severity levels
  (`bess-calc/.dependency-cruiser.cjs`) and its own pure-JS DOT graph
  renderer (used instead of madge's `--dot`, which shells out to a Graphviz
  binary not available in this environment or guaranteed in CI runners).

### Why these and not others

- **No code-graph/MCP indexing server, no Repomix.** The codebase is
  ~100 TypeScript files across `src/` and `server/`. A generated JSON/DOT
  import graph plus hand-written prose maps gives the mission's required
  capabilities (dependency understanding, impact analysis, visualisation,
  reduced context loading) without adding a long-running service, an index
  that can silently drift from the repo, or new maintenance surface. This
  is a scale-appropriate trade-off, not an oversight — if the codebase grows
  substantially, revisit this decision.
- **madge over a custom AST walker**: TypeScript-aware out of the box via
  the project's existing `tsconfig.json`, actively maintained, one flag to
  detect circular imports.
- **dependency-cruiser in addition to madge**: madge has no first-class
  pass/fail rule concept suitable for CI gating; dependency-cruiser's
  `forbidden` rules with `severity: error/warn` map directly onto "fail CI
  on a real violation, warn-only on cosmetic issues" — see
  `.dependency-cruiser.cjs`.

Both run locally via `node <entry.js>` (see "known limitations" below for
why not via `npx`), no network calls at runtime after `npm install`, no new
paid services.

## Architecture summary

The runtime is entirely under `bess-calc/`: a React/Vite SPA and an Express
API sharing a framework-independent TypeScript calculation engine
(`src/engine`, `src/battery`, `src/tariff`, `src/optimisation`, `src/import`),
with optional PostgreSQL persistence via Prisma. Full detail in
`docs/architecture/CURRENT_CODE_ARCHITECTURE.md` and `.agent/architecture/`.

Key finding from this pass, verified against the generated import graph
rather than assumed: **`src/battery/` is not currently imported by
`src/engine/`** — despite being conceptually part of the dispatch/
degradation story, there is no live import connecting them today. Any
future work connecting battery degradation into the dispatch/financial
engines should be aware this wiring doesn't exist yet, contrary to what the
module names might suggest.

No circular dependencies and no `engine-no-express`-rule violations were
found in `src/` or `server/` as of this snapshot (`npm run architecture:check`
passes).

## AI workflow recommendations

Documented in full in `.agent/context/agent-instructions.md`. Summary: query
`.agent/architecture/module-map.md` and `execution-flows.md` first; use the
reverse-dependency lookup in `dependency-map.md` against
`.agent/graph/import-graph.json` to scope which files a change actually
touches, rather than guessing from module names or the mission-brief-style
example; read only that scoped set; run `architecture:check` before adding
any new dependency into the engine layer.

## Maintenance instructions

- After a structural change (new module, moved file, new route, new Prisma
  model), run `npm run architecture:generate` from `bess-calc/` to refresh
  `.agent/graph/*`, then spot-check (and hand-edit if needed) the prose
  files in `.agent/architecture/` and
  `docs/architecture/CURRENT_CODE_ARCHITECTURE.md` — they are not
  auto-regenerated, by design (see `.agent/README.md#regenerating`).
- `npm run architecture:check` runs in CI (`.github/workflows/architecture.yml`)
  on any PR/push touching `bess-calc/src/**` or `bess-calc/server/**`. It
  fails only on `error`-severity dependency-cruiser rules (currently: engine
  modules importing `express`/`@prisma/client`). It does not diff generated
  file content against what's committed, so it will never fail from a
  documentation timestamp or incidental generator-output change.
- If `.agent/graph/*.json`/`.dot` files are committed and start growing
  large as the codebase grows, consider gitignoring them and running
  `architecture:generate` as a pre-task step instead of committing output —
  not done in this pass since current output is small (~35KB total).

## Known limitations

1. **Module-level import graph only, no function-level call graph.** madge
   and dependency-cruiser both operate on import statements, not on which
   functions call which. "Impact analysis" here means "which files import
   this file," not "which functions call this function." A change isolated
   to one function in a large file will still show the whole file's
   importers as potentially affected, even if most don't touch that
   function.
2. **DOT graphs are generated but not rendered to an image** in this pass —
   no Graphviz binary was available/assumed in this environment or
   guaranteed in CI. `.agent/graph/import-graph.dot` is valid Graphviz DOT
   text; rendering it to SVG/PNG is a manual follow-up step
   (`dot -Tsvg import-graph.dot -o graph.svg`) if a rendered image is
   wanted.
3. **The `.dependency-cruiser.cjs` `engine-no-express` rule is new** (added
   in this pass) and currently passes, but it's the first mechanical
   enforcement of a boundary that was previously convention-only (see
   `.agent/architecture/architecture-decisions.md`, decision #6) — it has
   not been battle-tested against a real attempted violation.
4. **Prose files in `.agent/architecture/` can drift from the generated
   graph** if someone changes the source tree and forgets to spot-check
   them (see maintenance instructions above). There is no automated diff
   check for this by design (regenerating and diffing would create false
   failures on legitimate structural changes) — it relies on the "after a
   structural change" step in `agent-instructions.md` being followed.
5. **The AI_CONTEXT_EFFICIENCY_REPORT.md comparison is one measured task**,
   not an average — the efficiency gain will vary by task, and is smaller
   for changes to very-high-blast-radius files like `src/types/bess.ts`.
